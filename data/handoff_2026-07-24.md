### site_screener.py

Client-facing opposition environment tiers. Scores every project in
`proposals.csv` into Low / Guarded / Elevated / High from five
percentile-ranked components with published weights:

```
local_activity  0.30   recency-weighted opposition events within 25 mi
                       (24-month half-life, undated at 0.25 weight,
                       statewide/federal scope excluded)
local_enacted   0.25   enacted local restrictions within 25 mi
county_model    0.25   calibrated county enacted-restriction score
state_activity  0.10   statewide legislative activity
org_capacity    0.10   named groups + petitions within 25 mi
```

Only `county_model` is a model output and it is labeled as such everywhere it
appears. The other four are descriptive counts, distances, and dates. Framed
as a directional screening indicator of the observed environment, explicitly
not a probability of any outcome. Missing components rank at the percentile
floor so they can never inflate a tier.

Runs inside `pipeline.yml` after the county layer, non-blocking, commits its
own outputs. Writes `data/site_screen.csv`, `data/site_screen_history.csv`
(append-only, idempotent within a day), and `data/site_screen_movers.md` (the
recurring newsletter artifact: tier changes and largest composite moves since
the prior run, threshold 3.0 points to sit above percentile-rebasing noise).

Single-site mode writes `signals/brief_<slug>.md` and `.json` with the
component table, nearest sourced activity, county context, and comparable
decided projects:

```
python site_screener.py --lat 39.11 --lon -77.56 --county Loudoun --state VA --mw 300 --name "Client Site"
python site_screener.py --batch
python site_screener.py --selftest
```

Verified run: 332 proposals scored, 128 Low / 107 Guarded / 78 Elevated / 19
High. 328 of 332 resolve to FIPS, 323 carry a county score.

Naming note: "screener" means screening a site for risk, portfolio-style. It
is not an approval gate and never blocks. If the name keeps reading as a gate,
`site_risk_profile.py` or `opposition_environment.py` are one-line renames.

### signal_harvest.py

GDELT 2.0 Doc API candidate harvester. Free, keyless, six query families,
stdlib only. Dedupes against every URL already cited in the database,
geotags headlines against the county gazetteer with confidence tiering
(high / medium / state_only / low / none), ranks a worklist by mechanism
keyword plus location resolution plus recency, demotes aggregator domains.

Never writes to `master_opposition.csv`. Writes `data/signal_candidates.csv`
and `data/signal_harvest_log.csv`.

Called by `build_master_csv.py` via `harvest_to_queue()` after the CSV is
written, so it dedupes against rows just ingested. Wrapped in a try/except
and behind an ImportError guard; a harvest failure cannot stop the CSV build.
CLI retained for ad-hoc runs and self-tests.

Originally built as a standalone `signal-harvest.yml` workflow. That was
withdrawn and folded into the existing ingest instead, because it overlapped
with the Google News RSS already in `build_master_csv.py`.

### scripts/build_master_csv.py

Two changes, both behavioral, both worth knowing:

1. **`fetch_news_rows` removed.** It was appending Google News RSS results
   directly into `master_opposition.csv` with Entity "Unknown", no state, no
   county, no date, no mechanism, no outcome. Those rows entered the source of
   truth unverified. Replaced by the harvest writing to a review queue.
   **Existing rows were not touched.** What changed is that new unverified
   rows stop being appended. If the RSS append needs to come back, it can be
   restored behind a flag.

2. **`data_source` provenance fixed.** `build_row` emitted the key
   `datasource` while the CSV header carries `data_source`, so the writer's
   `extrasaction="ignore"` silently dropped every provenance value. All 1,812
   rows currently have an empty `data_source`. Both keys are now written, so
   provenance persists under either spelling. Existing blanks are not
   backfilled by this change.

`feedparser` dropped from the workflow install.

## Item 1 in detail: the 369 untagged rows

These are the rows the removed RSS step left behind. Every one has blank
Opposition Type, Entity "Unknown", blank State, and Status "ongoing". They
currently pass through to the QC gate, the county aggregator, and every count
that could be quoted externally.

**Run this first.** It answers the question the whole task hinges on:

```
python3 -c "
import csv, collections
r = list(csv.DictReader(open('master_opposition.csv')))
bad = [x for x in r if not x.get('Opposition Type','').strip()]
print('untagged rows:', len(bad))
print('with a Source URL:', sum(1 for x in bad if x.get('Source URL','').strip()))
print('by year:', collections.Counter((x.get('Date') or 'undated')[:4] for x in bad).most_common())
"
```

**Three options, leading to different builds:**

- **Quarantine.** Move to `master_opposition_untagged.csv`, exclude from all
  counts. Cleanest, fastest, loses whatever signal is in them.
- **Tag in place.** Add a `verification_status` column marking them
  unverified, keep them in the file, exclude at the QC gate. Preserves
  everything, more plumbing.
- **Backfill.** Run each Source URL through the geotagging and mechanism
  logic `signal_harvest.py` already implements, promote what resolves
  cleanly, quarantine the rest. Best outcome, longest build.

Recommendation is backfill with quarantine as the fallback, since the
harvester's tagging code already exists and can be pointed at these rows.
Decision depends on how many carry a usable URL, which the command above
answers.

One complication to expect: the Source URLs on these rows are Google News
redirect links (`news.google.com/rss/articles/...`), not publisher URLs. They
may need resolving to a final destination before domain or outlet inference
is possible. Worth checking one by hand before assuming the backfill path is
open.

## Correction to carry forward

MAPIE was originally listed as the top priority. That was wrong in scope.
Conformal intervals need a model with a target to conform against, and the
screener composite is a percentile rank with no ground truth, so MAPIE cannot
wrap it. It applies to `county_policy_model.py` and `outcome_model.py`. On the
outcome model, which sits near chance, the intervals will come back very wide.
That is the honest result and worth having, but it will read as more candid
rather than stronger. Scope MAPIE to the county model, where calibration
already exists.
