# Data Center Opposition Intelligence Platform Constitution

This constitution governs every spec, plan, task list, and implementation produced
with Spec Kit in `pricephillips/data-center-map`. It restates standing rules that
already live in README.md, ARCHITECTURE.md, and IDENTIFIABILITY.md. Where this file
and a standing document disagree, the standing document governs and this file is
amended to match.

## Core Principles

### I. Defensibility Above All (NON-NEGOTIABLE)

Every external-facing claim MUST be traceable to a sourced URL, verifiable, and
never overstated. Outcomes are never inferred from prose. "Decided" means terminal
dispositions only (`blocked_confirmed`, `restricted_conditional`,
`advanced_confirmed`); pending and unverified records are excluded from
decided-case statistics. `ext_` records never enter the modeling frame. A spec
that needs a claim the data cannot support MUST scope the claim down, not the
evidence standard.

### II. Activity-Descriptive Vocabulary (NON-NEGOTIABLE)

Generated artifacts and client-facing copy use the outcome ladder in README.md
(`advanced_confirmed`, `restricted_conditional`, `blocked_confirmed`, `pending`,
plus the `_unverified` variants used internally). Scorekeeping vocabulary is
prohibited. `leak_audit.py` is a hard CI gate; every feature that writes a new
artifact MUST leave `python leak_audit.py --tier blocking` at zero blocking hits.

### III. Legislative Outcome Discipline

A bill that passed committee or one chamber is pending, not enacted. Terminal
dispositions (signed, vetoed, sine die, failed floor vote, withdrawn) outrank
in-progress milestones. The legislative stage ladder governs; no feature may
shortcut it.

### IV. Descriptive, Not Causal

Per IDENTIFIABILITY.md, no dollar or delay figure is ever described as caused by
or attributable to opposition. Client-facing text describes associations and
observed histories, never counterfactuals. Feature importance is predictive, not
causal. Deep learning is not part of the platform and MUST NOT be claimed.

### V. Calibrated, Gated Models

Models predict observable outcomes (probability of block, time to decision,
condition tier). Dollar figures come only from the documented cost-translation
layer with explicit assumptions. Outputs are calibrated ranges with uncertainty,
never unexplained point estimates. Training labels are decided cases only. No
model is promoted except through `calibration_gate.py`. Changes to headline
metrics are acceptable when input precision, coverage, or architectural
separation improves; they are never a reason to revert.

### VI. Statistic Reproducibility

Every numeric claim in a client-facing deliverable MUST be re-derived from the
current CSV before publication, using `outcome_defensible` filtered to terminal
outcomes and a normalized `State` field. Small drift between a snapshot and a
newer CSV is data growth; note it, do not treat it as a discrepancy. County-level
opposition rates are not computable at current density and MUST NOT be published.
Group-level outcome columns (`decided`, `confirmed_blocks`, `blocked_share`) are
permanently internal.

### VII. Additive and Backward-Compatible

Features never break existing behavior or rename stable files
(`master_opposition.csv` above all). New columns are appended; absent them,
behavior is unchanged. Suggestions and triage output never auto-apply; they are
drafts for human review.

### VIII. Layer Ownership

One writing process per file. No writer crosses a layer boundary undeclared.
`configs/layers.json` is the machine-readable declaration and `layer_audit.py`
enforces it. Any plan that adds a writer or a cross-layer write MUST declare it in
`configs/layers.json` with its reason, and update ARCHITECTURE.md in the same
change.

### IX. Selftested Modules

Every pipeline module ships a `--selftest` entry point. A new module is wired into
the blocking selftest step of `pipeline.yml` before its outputs are relied on.

## Data and Architecture Constraints

- Single source of truth for the map and dashboard: `master_opposition.csv`,
  regenerated by GitHub Actions on push. The unit of analysis for modeling is the
  project entity, not the opposition event.
- All frontend fetch chains put `raw.githubusercontent.com` first; GitHub Pages
  sends no CORS headers and Notion or Simple.ink embeds fail silently otherwise.
  Loaders show a visible error banner on failure.
- Iowa (`pricephillips/iowa-dc-tracker`) is a downstream consumer triggered by the
  `csv-updated` repository dispatch, never a parallel pipeline.
- Committing workflows use the rebase-and-retry pattern; workflow triggers are
  deduplicated to avoid auto-commit races.
- Decision dates enter `project_decision_dates.csv` only with a source and URL.
  Year-precision dates are excluded from the time axis rather than floored.
- Formatting: no em-dashes in any deliverable; LF line endings in all CSVs;
  statistical terms are defined on first use in client-facing copy.

## Development Workflow and Quality Gates

- Work proceeds in numbered passes. Claude produces finished drop-in files with
  exact placement instructions; Price owns all git operations. Spec Kit's git
  extension is intentionally not installed.
- Spec Kit flow: `/speckit-specify` -> `/speckit-clarify` (when scope is
  ambiguous) -> `/speckit-plan` -> `/speckit-tasks` -> `/speckit-analyze` ->
  `/speckit-implement`. Specs live in `specs/NNN-feature-name/`.
- Every plan's Constitution Check MUST confirm, before implementation:
  1. `python leak_audit.py --tier blocking` returns 0 blocking hits.
  2. `python layer_audit.py` reports 0 undeclared findings.
  3. `--selftest` passes on every touched or new module.
  4. `node --check` passes on any touched inline or standalone JS.
  5. No em-dashes and no CRLF in touched deliverables and CSVs.
  6. Any docx deliverable passes validation with the `--original` flag.
- Pending CI changes that cannot be pushed from a sandbox are staged as
  `docs/pending_*.patch` with a matching `.md`, per existing practice.

## Governance

This constitution supersedes Spec Kit defaults and generic agent guidance for this
repository. Every spec, plan, and task list MUST pass the Constitution Check in
`plan-template.md`; a violation is either removed or justified in the plan's
Complexity Tracking table. Amendments are made by editing this file with an updated
Sync Impact Report and a version bump: MAJOR for removing or redefining a
principle, MINOR for adding one, PATCH for wording. Standing documents
(README.md, ARCHITECTURE.md, IDENTIFIABILITY.md, PHASE_STATUS.md) remain
authoritative for their subjects.
